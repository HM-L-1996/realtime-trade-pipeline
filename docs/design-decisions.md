# 설계 판단

> 무엇을 골랐는지보다 **무엇을 포기했는지**를 남긴다.

## 처리 엔진: Flink

**이 규모에는 Flink 가 과하다.** 종목 2개에 초당 20건 남짓이면 Kafka Streams 로 충분하고,
운영 부담도 훨씬 가볍다. 그런데도 Flink 를 고른 이유는 처리량이 아니라 **관측 가능성**이다.

이 프로젝트가 채우려는 공백은 "스트림 처리 의미론" 이다. 그러려면 워터마크·체크포인트·
세이브포인트를 **밖에서 만질 수 있어야** 하고, 잘못 만졌을 때 결과가 어떻게 틀어지는지가
보여야 한다. 세 후보를 그 기준으로 봤다.

| | 이벤트타임 워터마크 | 상태 이관 | 이 프로젝트에서 |
|---|---|---|---|
| **Flink** | 소스 단위로 노출. 유휴 처리·허용 지연을 따로 설정 | savepoint 로 명시적 이관, `uid` 고정 | **채택** |
| Kafka Streams | grace period 로 표현. 유휴 파티션 개념이 약함 | changelog 토픽에 묶임 | 제외 |
| Spark Structured Streaming | 마이크로배치라 워터마크가 배치 경계에 종속 | 체크포인트 디렉터리 호환성이 까다로움 | 제외 |

실제로 이 선택이 값을 한 자리가 있다.

- **유휴 파티션으로 워터마크가 멈추는 것**을 `withIdleness` 를 껐다 켜며 대조할 수 있었다.
  Kafka Streams 였다면 같은 조건을 만들기 어려웠다.
- **savepoint 재개와 cancel 재시작의 차이**를 손실 0 대 −67% 로 갈라 볼 수 있었다.
  상태 이관이 명시적인 API 로 노출돼 있어서 가능했다.
- **워터마크 지연을 0으로 줘도 드롭이 0~4,255 로 갈리는 것**을 관측했다.
  "설정은 보장이 아니다" 라는 결론은 설정을 직접 만질 수 있어야 나온다.

- 포기한 것: 운영 부담. JobManager·TaskManager·체크포인트 스토리지가 따로 필요하고
  **부가 연산자 하나의 실패가 잡 전체를 재시작시킨다**(실제로 장중에 당했다)
- 얻은 것: 스트림 의미론을 **설정으로 깨뜨리고 결과로 확인하는** 실험이 가능해짐

## 저장: ClickHouse

검증이 목적이므로 **조회가 즉시 되어야 하고 중복이 보여야 한다.** 그 둘이 기준이었다.

| | 조회 지연 | 중복이 보이는가 | 운영 부담 |
|---|---|---|---|
| **ClickHouse** | 즉시 | `MergeTree` 면 그대로 쌓인다 | 단일 노드로 충분 |
| Iceberg 단독 | **체크포인트 주기만큼**(10초) | exactly-once 라 애초에 안 생긴다 | 카탈로그가 따로 필요 |
| TimescaleDB | 즉시 | 보이지만 upsert 가 기본 관례 | Postgres 운영 |

**Iceberg 를 단독으로 쓰면 이 프로젝트의 검증이 성립하지 않는다.** 중복이 안 생기는 것은
좋은 성질이지만, 그러면 "at-least-once 가 실제로 무엇을 하는가" 를 보여줄 방법이 없어진다.
그래서 ClickHouse 를 주 저장소로 두고 **Iceberg 는 두 번째 싱크로 나란히** 붙였다(아래 참고).

TimescaleDB 는 조회 성능 자체보다 **운영을 하나 더 배우는 비용**에서 걸렸다.
이 프로젝트가 채우려는 공백과 축이 다르다. ClickHouse 는 실무에서 도입을 검토 중이라
학습 목적이 겸해진다는 점도 고려했다.

**실측으로 확인한 것:** 두 저장소에 같은 캔들을 흘려 대조했더니
시가·고가·저가·종가·거래량·체결 수가 **전 항목 일치**했다. 다른 것은 기록 횟수뿐이다
(TaskManager 강제 종료 시 ClickHouse 22행/중복 2, Iceberg 20행/중복 0).
즉 저장소를 바꿔서 값이 달라지지는 않는다 — 갈리는 것은 **장애 때의 거동**이다.

- 포기한 것: 장기 보관과 스키마 진화. ClickHouse 는 파케이 파일 기반 레이크가 아니다
- 얻은 것: 즉시 조회와 **중복이라는 관측 가능한 실패 신호**

### 캔들 테이블 엔진: MergeTree (ReplacingMergeTree 아님)

`ReplacingMergeTree((symbol, window_start))`를 쓰면 같은 윈도가 두 번 적재돼도
백그라운드 머지에서 조용히 하나로 접힌다. 운영 관점에선 그게 맞지만,
**이 프로젝트에서는 중복이 보이지 않으면 검증할 것이 사라진다.**
exactly-once가 지켜지는지를 "설정이 켜져 있다"가 아니라 **결과로** 확인하는 게 목적이므로,
중복을 저장 계층에서 감추지 않고 `MergeTree`에 그대로 쌓은 뒤
조회 시점에 `candles_1m_dedup` 뷰의 `write_count`로 드러낸다.

- 포기한 것: 조회 편의성, 저장 공간
- 얻은 것: `write_count > 1`이라는 관측 가능한 실패 신호

## 파티션 키 설계

Kafka 토픽 `trades.raw`를 **파티션 3개**로 만들고 `symbol`을 키로 쓴다.
같은 종목은 같은 파티션에 들어가므로 종목 단위 순서가 보장되고,
서로 다른 종목은 병렬 처리된다. Flink `parallelism.default`와 TaskManager 슬롯도 3으로 맞췄다.

**토픽을 auto-create에 맡기지 않는다.** `KAFKA_AUTO_CREATE_TOPICS_ENABLE=false`로 끄고
`kafka-init` 컨테이너에서 명시 생성한다. auto-create에 맡기면 파티션 수가 조용히 1이 되어,
"파티션을 늘렸을 때 종목별 순서가 어떻게 되는가"라는 실험의 전제 자체가 무너진다.
설정이 조용히 다르게 적용되는 것이 이 프로젝트에서 가장 피해야 할 종류의 사고다.

- 포기한 것: 종목을 늘릴 때 파티션 재조정이 필요
- 얻은 것: 순서 보장의 근거가 명시적이고, 깨뜨리는 실험이 가능해짐

## 윈도우 / 워터마크 전략

1분 텀블링 윈도, **워터마크 지연 5초, 유휴 타임아웃 10초, 허용 지연 0초**다.
세 값을 이렇게 잡은 근거가 각각 있다.

#### 워터마크 지연 5초 — 소스의 실측 역행 폭에서 나왔다

수집기가 `Sequencer` 로 **이벤트타임 역행을 세고 있다.** 005930 하나에서만 2,195건이었다.
즉 이 소스는 순서를 보장하지 않고, 그 폭을 알아야 지연 허용치를 정할 수 있다.
5초는 관측된 역행을 덮으면서 결과 지연을 1분 윈도의 10% 안에 두는 값이다.

#### 허용 지연 0초 — 버려지는 것을 보려고 일부러 0이다

운영이라면 몇 초 두는 게 맞다. 여기서는 **버려진 건수가 워터마크 설정과 정확도를 잇는
유일한 근거**이므로 0으로 두고 전부 `dead_letters` 로 남긴다.
재발행이 없으니 `write_count` 도 중복 신호로만 쓸 수 있다.

#### 유휴 타임아웃 10초 — 안 두면 파이프라인이 멈춘다

종목 2개에 파티션 3개라 **파티션 하나는 항상 비어 있다.** 워터마크는 모든 분할의 최소값을
따라가므로 유휴 처리를 안 하면 윈도가 영원히 닫히지 않는다. 실측으로 확인했다.

#### 그런데 설정만으로는 정해지지 않는다

이 절에서 가장 중요한 결론이다. **같은 입력·같은 워터마크 설정에서 드롭이 0~4,255 로 갈렸다.**
실제 허용치를 정한 것은 설정이 아니라 **파티션 수와 소비 상태**(실시간 추종인가 캐치업인가)였다.

그리고 유휴 처리로도 못 막는 구간이 있다. **모든** 파티션이 조용하면 워터마크를 끌어줄 것이
없다. 마감 동시호가(15:20~15:30)가 매일 그렇고, 그때 15:19 윈도가 **11분 늦게** 닫혔다.

- 포기한 것: 늦게 온 체결. 허용 지연이 0이므로 워터마크를 지난 것은 전부 버린다
- 얻은 것: 버려진 건수가 계측되고, 설정을 바꾸면 정확도가 어떻게 움직이는지 대조할 수 있음

## 배포: Kubernetes (Flink Kubernetes Operator)

스트리밍 잡을 K8s에 올리는 것은 배치 워크로드를 올리는 것과 성질이 다르다.
Flink 잡은 **상태를 가진 장기 실행 프로세스**이므로 —

- TaskManager Pod이 죽었을 때 체크포인트에서 복구되는가, 상태는 유지되는가
- 잡을 재배포할 때 savepoint로 상태를 넘길 수 있는가 (무중단 배포)
- 백프레셔 상황에서 오토스케일이 유효한가, 오히려 상태 재분배 비용이 더 큰가

이 질문들은 로컬 실행으로는 만날 수 없다. **장애 실험(`failure-notes.md`)의 절반이 여기서 나온다.**

> 개발 순서: **docker-compose로 먼저 동작시킨 뒤 K8s로 옮긴다.**
> 처음부터 K8s에서 시작하면 처리 로직 버그와 클러스터 문제가 뒤엉켜 시간이 배로 든다.

## 관측: Prometheus + Grafana

계측이지 스코프 확대가 아니다. `failure-notes.md`의 항목들이
"백프레셔가 **어디서** 발생하고 **어떻게 관측되는가**", "복구에 **얼마나** 걸리는가" 형태인데,
숫자가 없으면 이 문서를 쓸 수가 없다. Flink가 Prometheus 리포터를 내장하므로 연결 비용도 낮다.

보는 지표: 체크포인트 소요/실패, backpressure ratio, Kafka consumer lag,
윈도 late-record drop 수, TM 재시작 후 복구 시간.

## 배포: ArgoCD (K8s 단계)

학습 목적으로 넣었다. 단일 노드 클러스터에서 GitOps 가 실제로 무엇을 바꾸는지 보려는 것이고,
특히 **상태를 가진 스트리밍 잡**에서 savepoint 인계와 "선언 상태로 수렴" 이 어떻게 부딪히는지가
관심사였다. 세 가지를 배웠다.

#### 1. 배치와 다른 점 — 스펙을 바꾸면 상태를 옮겨야 한다

`FlinkDeployment` 의 `upgradeMode: savepoint` 는 스펙이 바뀌면 savepoint 를 뜬 뒤
그 지점에서 재개한다. 배치 워크로드라면 그냥 새 파드를 띄우면 되지만, 여기서는
**"선언한 상태로 수렴" 이 곧 "잡을 한 번 멈춘다" 를 뜻한다.** 재스케일 한 번에 1분 59초였다.

그래서 `values.yaml` 의 사소한 변경도 배포 비용이 있다. 이미지 태그를 올리는 것과
알람 규칙 한 줄을 고치는 것이 같은 무게가 아니다.

#### 2. `Synced` 는 "적용됐다" 가 아니다

가장 값진 것은 이쪽이다. ArgoCD 가 **새 리비전을 `Synced/Healthy` 로 표시하면서
실제로는 이전 리비전을 적용해 둔** 상태를 만났다.

```
sync.status                             Synced
sync.revision                           3d0859f   <- 새 커밋
operationState.operation.sync.revision  5346d64   <- 실제로 적용한 것
```

원인은 버전 격차였다. 클러스터가 v1.37 인데 ArgoCD 는 v2.13.2 라
`status.terminatingReplicas` 를 몰라 **모든 Deployment 의 diff 계산이 실패**했다.
그런데 그 실패가 화면에는 초록불로 나왔다 — **모른다는 것과 같다는 것이 같은 색이었다.**

그래서 `scripts/verify.sh` 0번이 **실제 적용 리비전**을 HEAD 와 대조한다.
`sync.status` 만 보면 안 된다는 것이 이 프로젝트가 GitOps 에서 얻은 가장 실용적인 교훈이다.

#### 3. K8s 기본값이 영원한 OutOfSync 를 만든다

리소스는 멀쩡한데 GitOps 만 빨간불인 상태를 오래 방치했다.
**그 상태를 두면 진짜 drift 가 그 안에 묻힌다.** `ignoreDifferences` 를 근거를 조사해
두 건으로 좁혔다 — 넓게 잡으면 같은 문제가 반대 방향으로 생긴다.

- 포기한 것: 배포 속도. `kubectl apply` 로 즉시 고치는 대신 커밋·푸시·동기화를 거친다.
  실제로 장애 대응 중에 이 지연이 부담이 됐다
- 얻은 것: 클러스터 상태가 저장소에 남는다. 그리고 **초록불을 의심하는 습관**

## 분석: Superset (마지막 단계)

**아직 붙이지 않았다.** CLAUDE.md 가 정한 순서의 마지막 단계이고,
"파이프라인이 검증까지 끝난 뒤에" 라는 조건을 스스로 걸어 두었다.

붙이면 무엇을 볼 것인지는 정해 두었다 — ClickHouse 에 연결해
**공식 캔들 대비 오차의 시간 분포**를 본다. `verify.sh` 가 표로 주는 것과 같은 내용이지만,
분 단위로 흩어진 오차를 눈으로 보면 **패턴이 다른 것끼리 구분**하기 쉽다.
지금까지 나온 어긋남이 실제로 세 종류였다.

| 모양 | 원인 |
|---|---|
| 부호가 대칭이고 총량 보존 | 경계 배정(09:05 −2,388 / 09:06 +2,388) |
| 한쪽으로만 음수, 한 윈도에 국한 | 소스 단절(2.226초에 −1.7%) |
| 한쪽으로만 음수, 앞뒤는 정상 | 잡이 죽은 채 오프셋만 넘어간 것 |

표로는 이 셋을 매번 눈으로 가려야 하는데, 시계열로 겹쳐 보면 즉시 갈린다.

**Grafana 가 이미 있는데 왜 또 붙이는가**도 정리해 둔다.
Grafana 는 지표(Prometheus) 를 본다 — 파이프라인이 **지금 건강한가**를 묻는 도구다.
Superset 은 ClickHouse 를 본다 — **결과가 맞았는가**를 묻는 도구다.
질문이 다르므로 도구가 둘인 것이 중복이 아니다.

- 포기한 것: 아직 없다. 안 붙였다
- 남은 위험: 이 프로젝트에서 마지막에 붙이는 것들이 검증을 흔든 전례가 있다
  (Iceberg 싱크가 장중에 파이프라인을 멈춰 세웠다). **운영 잡을 건드리지 않는 방식**으로 붙여야 한다

## 수집 계층: 소스가 lossy하다는 전제

토스 WebSocket 체결 스트림에는 **시퀀스 번호도 체결 ID도 없고, 문서가 스스로 lossy하다고 명시**한다.
매수/매도 구분과 누적 거래량도 없다. 이것이 이 프로젝트의 검증 설계를 바꾼다.

공식 캔들과 내 집계가 어긋났을 때 원인이 두 갈래이기 때문이다.

1. 내 파이프라인 문제 (워터마크·윈도우·체크포인트)
2. 소스 프레임 유실 — 내 잘못이 아님

**이 둘을 분리하지 못하면 `validation.md`의 수치가 아무것도 증명하지 못한다.**
그래서 `trades_raw`에 수집기가 매기는 `recv_seq`(연결별 프레임 일련번호)와
`conn_id`(재연결 구분)를 처음부터 넣는다. 나중에 붙이면 그 전 데이터에는 소급되지 않는다.

체결 ID가 없으므로 멱등키도 소스에서 받을 수 없다.
`(symbol, timestamp, price, volume)`은 같은 ms에 동일 체결이 실제로 발생하므로 유일하지 않다.
→ 수집기가 `(symbol, event_time)` 안의 `seq_in_ms`를 부여한다.

`price`·`volume`은 `Decimal64`로 둔다. 소스가 문자열로 주는데
`Float64`로 받으면 부동소수 오차가 그대로 "검증 오차"로 둔갑한다.

## 원본 체결 보관: 집계 잡에 붙였다

`trades_raw` 를 채우는 주체가 없어 `recv_seq` 설계가 실현되지 않고 있었다.
수집기가 연결별 일련번호를 매기는데 그 값이 어디에도 남지 않으면
소스 유실을 측정할 수 없고, 그러면 공식 캔들과의 차이가 **내 버그인지 소스 유실인지
끝까지 구분되지 않는다.**

별도 적재 서비스를 만들지 않고 집계 잡에 두 번째 싱크로 붙였다.
그 잡이 이미 스트림을 읽고 있어서 서비스를 하나 더 띄울 이유가 없다.

- 포기한 것: **집계와 보관의 수명이 묶인다.** 잡이 죽으면 보관도 멈춘다
- 얻은 것: 서비스 하나, 그리고 같은 체크포인트 경계에서 두 싱크가 함께 커밋된다

> **실측 대가는 이보다 컸다(2026-09-02).** 부하 실험에서 이 적재를 끄니
> 처리량이 **6,370 → 103,031 건/s 로 16배** 뛰었다.
> 소스 태스크에 체인돼 있어 ClickHouse HTTP 왕복이 소스 시간의 대부분을 먹는다.
> 평상시 유입(초당 60건)에서는 문제가 되지 않지만,
> **밀린 구간을 따라잡을 때는 이 차이가 복구 시간을 그대로 결정한다.**
> 분리하거나 배치를 키우는 것이 답이고, 지금은 대가를 알고 붙여 둔 상태다.

보관이 집계와 독립적으로 중요해지면 그때 분리한다. 지금은 보관의 목적이
"집계를 검증하는 것" 이므로 수명이 묶여도 손해가 없다.

적재량이 캔들의 수백 배(초당 60행 vs 분당 2행)라 `--archive-trades false` 로 끌 수 있다.

## 장 운영 시간과 리플레이

정규장은 09:00–15:30(KST)이지만 **토스가 주는 캔들은 20:00까지 이어진다.**
넥스트레이드(대체거래소) 애프터마켓 때문이다 — 실제 데이터를 받아보고 확인했다(2026-08-31).
처음엔 "하루 6.5시간" 으로 적었으나 실제로는 **08:00–20:00, 약 12시간** 흐른다.
그래도 24/7 크립토와 달리 평일 주간에만 흐르는 것은 같다.

장시간 구동이 필요한 실험(체크포인트 누적, 상태 증가, 백프레셔)을 자연 데이터로만 하면 진도가 안 나간다.

→ **저장한 원본 체결을 Kafka로 리플레이하는 경로를 우선순위 높게 만든다.**
이 경로는 재처리·순서 역전·지연 도착 실험에도 그대로 쓰인다.
`trades_raw`의 TTL을 정할 때 이 용도를 고려해야 한다(현재 7일).

## 버전 선택

| 대상 | 선택 | 이유 |
|---|---|---|
| Flink | 1.20 (LTS) | Kafka 커넥터·Kubernetes Operator 호환이 검증된 버전. 2.x의 신버전 이슈와 처리 로직 버그가 뒤엉키는 것을 피한다 |
| Kafka | 3.9.0 (KRaft) | Zookeeper 없는 단일 브로커. 로컬 구성 단순화 |
| ClickHouse | 24.8 (LTS) | |

## 체크포인트 / 트랜잭션 설정

- `execution.checkpointing.interval: 10s` — 실험 회전을 빠르게. 복구 실험에서 대기 시간이 짧아야 반복이 된다
- `state.backend: rocksdb` + incremental — 상태가 커지는 실험을 염두
- `RETAIN_ON_CANCELLATION` — 잡을 죽여도 체크포인트가 남아야 복구 실험이 가능
- **`KAFKA_TRANSACTION_MAX_TIMEOUT_MS: 900000`** — **현재 이 파이프라인에서는 아무 효과가 없다.**
  이 설정은 Flink 의 Kafka 트랜잭셔널 싱크(`KafkaSink` + `EXACTLY_ONCE`)를 보호하는 것인데,
  이 잡은 Kafka 를 **소스로만** 읽고 쓰지 않는다. 유일한 싱크는 HTTP 기반 ClickHouse 다.

  처음에 "Flink exactly-once 싱크는 Kafka 트랜잭션을 쓰므로 이 값을 늘려야 한다" 고 적었으나,
  그건 Flink-Kafka EOS 튜토리얼의 설명을 **우리 구조에 적용 가능한지 확인하지 않고 옮겨 적은 것**이었다.
  설정은 무해하므로 남겨 두되(나중에 Kafka 싱크를 붙이면 필요하다) 근거는 바로잡는다.

  > 교훈은 설정값 자체가 아니라 **"왜 필요한지 설명을 붙였는데 그 전제가 우리 아키텍처에
  > 존재하지 않았다"** 는 것이다. 근거가 그럴듯하면 검증을 건너뛰게 된다.

## 시계: 이벤트타임은 소스, 처리 시각은 우리 것

수집기가 `ingest_time` 을 함께 기록하는데, 이 값과 `event_time` 의 차이를 재 보니
**94.4%의 체결이 이벤트 시각보다 먼저 도착한 것으로 나온다**(중앙값 −67ms).
우리 시계가 소스보다 뒤에 있다는 뜻이다.

더 중요한 것은 그 값이 **고정 오프셋이 아니라 움직인다**는 점이다.

```
08:00  −289ms
09:00   −95ms
10:20   −57ms   (최소)
11:30   −69ms
```

단조 수렴하다 다시 벌어지는 모양 — NTP 가 로컬 시계를 교정해 들어가는 전형적인 형태다.
Docker Desktop VM 의 시계 드리프트로 보인다.

이것이 설계에 주는 결론은 둘이다.

- **윈도잉은 영향받지 않는다.** 이벤트타임으로 소스가 준 `timestamp` 만 쓰기 때문이다.
  `ingest_time` 을 이벤트타임으로 썼다면 집계가 시계 드리프트를 그대로 받아 흔들렸을 것이다
- **"소스 지연" 지표는 우리 시계를 믿어야 성립한다.** 그 전제가 깨져 있으므로
  이 값을 절대 기준으로 쓸 수 없다. 초기 구현이 `max(0, lag)` 으로 음수를 뭉개
  관측값의 94%를 0으로 만들고 있었다 — 지표가 현상을 가린 사례다

## 재배포: 시작 오프셋과 savepoint

`OffsetsInitializer.earliest()` 를 기본으로 두었다가 **재배포 한 번에 420개 윈도가 중복**됐다.
토픽 전체를 다시 처리하는데 싱크가 멱등하지 않으니 이미 적재된 윈도가 또 쓰인다.

기본을 `committedOffsets(EARLIEST)` 로 바꿨다. 커밋 오프셋이 없을 때(첫 배포)만
처음부터 읽으므로 첫 실행과 재배포가 둘 다 의도대로 동작한다.
재처리·리플레이 실험은 `--start-offsets earliest` 로 **매번 의식적으로 켠다.**
감춰진 기본값이면 실수로 전체 재처리를 유발하고, 그 사실을 중복이 쌓인 뒤에야 알게 된다.

### 그래도 savepoint 가 필요한 이유

`committed` 는 **오프셋만** 이어받는다. 윈도 누산기 같은 **연산자 상태는 버려진다.**
잡을 취소하는 순간 열려 있던 윈도의 부분 집계가 사라지고, 재시작하면 그 윈도는
남은 체결만으로 다시 만들어져 **거래량이 모자란 캔들**이 된다.

상태까지 넘기려면 savepoint 로 멈추고 거기서 재개해야 한다.

```bash
# 상태를 남기며 중단
docker exec rtp-jobmanager flink stop --savepointPath /flink/savepoints <jobId>

# 그 지점에서 재개 (오프셋 + 상태 함께)
docker exec rtp-jobmanager flink run -d -s /flink/savepoints/savepoint-xxxx   /flink/jobs/aggregator-0.1.0.jar --topic trades.raw --group-id rtp-candle-live
```

savepoint 재개가 성립하려면 상태 연산자마다 `uid` 가 고정돼 있어야 한다.
그래서 `candle-1m`, `clickhouse-candles`, `late-trades` 에 uid 를 박아 두었다.

- 포기한 것: 절차가 한 단계 늘어난다
- 얻은 것: 윈도 경계에서 잘린 캔들이 생기지 않는다

### 실측으로 확인했다 (2026-08-31)

윈도가 열려 있는 중간에 두 방식으로 재배포하고 정답과 대조했다.

| 방식 | 진행 중이던 윈도 | 정답 대비 |
|---|---|---|
| `flink stop --savepointPath` → `run -s` | 18,526 | **정확히 일치** |
| `flink cancel` → `run` (committed) | 6,871 | **−67%** |

`cancel` 은 상태를 버리고, 재시작은 커밋된 오프셋(=마지막 체크포인트)에서 시작한다.
윈도 시작부터 그 지점까지의 체결은 **상태에서도 사라지고 다시 읽히지도 않는다.**

**중복과 손실은 별개 문제다.**

| | 중복 | 진행 중 윈도 손실 |
|---|---|---|
| `earliest` 재시작 | 발생 | 없음 |
| `committed` 재시작 | 없음 | **발생** |
| savepoint 재개 | 없음 | 없음 |

`committed` 기본값은 중복만 막는다. **운영에서 잡을 만질 때는 savepoint 가 기본이어야 한다.**

  백프레셔 대응 실험은 Flink 자체 오토스케일러로 다뤘다(아래 참고)
- **Flink 오토스케일러를 운영 잡에 켜는 것** — 실험은 했고 결론은 "켜지 않는다" 다

### Iceberg 는 두 번째 싱크다 - ClickHouse 를 대체하지 않는다

같은 캔들을 두 곳에 쓴다. 목적은 저장소를 늘리는 것이 아니라
**전달 보장의 차이를 결과로 보이는 것**이다.

| | ClickHouse | Iceberg |
|---|---|---|
| 커밋 시점 | 배치가 차면 바로 | 체크포인트 완료 시 |
| 보장 | at-least-once | exactly-once |
| 조회 지연 | 즉시 | **체크포인트 주기만큼**(10초) |

**공짜로 얻는 보장이 아니다.** Iceberg 쪽은 커밋해야 보이므로 그만큼 늦는다.
즉시성이 필요한 조회는 ClickHouse 쪽을 봐야 한다.
이 트레이드오프를 문장으로 적는 대신 같은 파이프라인에서 나란히 돌려
`k8s/experiments/dual-sink.yaml` 로 비교할 수 있게 해 두었다.

스키마는 두 저장소가 **같은 Decimal 정밀도**를 쓴다. 그러지 않으면
반올림 차이가 "검증 오차" 로 둔갑한다.

**검증했다(2026-09-04).** TaskManager 를 강제 종료해 "쓴 뒤 커밋 전" 구간을 만든 결과,
같은 20윈도에서 ClickHouse 는 22행(중복 2), Iceberg 는 20행(중복 0)이었다.
값 자체는 전 항목 일치한다 — 갈리는 것은 기록 횟수뿐이다.

붙이는 과정에서 벽이 셋 있었고 그중 하나는 **장중에 운영 파이프라인을 멈춰 세웠다.**
`failure-notes.md` 의 "Iceberg 싱크를 붙이며 만난 벽 세 개" 와
"부가 기능 하나가 운영 파이프라인을 장중에 멈춰 세웠다" 를 참고한다.

### 오토스케일러를 켜지 않는다

Flink Operator 1.15 의 오토스케일러로 실험한 뒤 내린 결론이다.

**종목이 2개인 한 병렬도를 올려도 나눌 데이터가 없다.** 수집기가 종목을 키로 보내므로
같은 종목은 같은 파티션에 모이고, 파티션이 6개여도 실제로 채워지는 것은 2개다.
그 상태에서 오토스케일러는 병렬도를 6까지 올렸고 **subtask 4개가 아무것도 하지 않았다.**

이득을 분해해 보면 이렇다(CPU 총량을 고정하고 측정).

| | 처리량 | |
|---|---|---|
| 병렬도 2 · CPU 0.5 | 6,024 건/s | |
| 병렬도 2 · CPU 1.5 | 28,279 건/s | 자원 3배 → **4.69배** |
| 병렬도 6 · CPU 1.5 | 39,202 건/s | 병렬도 3배 추가 → **1.39배** |

**"스케일 켰더니 6.5배" 의 대부분은 병렬화가 아니라 자원이었다.**
그리고 재스케일 한 번에 **1분 59초** 멈춘다(`upgradeMode: savepoint`).

종목 24개로 키만 늘린 대조군에서는 같은 병렬도 변화가 **2.28배**를 냈다.
즉 오토스케일은 **키가 나뉘는 만큼만** 듣는다.

이 프로젝트는 종목을 소수만 다루기로 했으므로(범위를 넓히지 않는다는 원칙),
오토스케일을 켤 조건 자체가 성립하지 않는다. 늘려야 한다면 병렬도가 아니라
**종목 수를 먼저** 늘리고 그때 파티션 수를 같이 조정해야 한다.
자세한 것은 `failure-notes.md` 의
"오토스케일이 6.5배를 냈는데 그중 병렬화의 몫은 1.39배였다".

### 거래가 없는 1분을 캔들로 만들지 않는다

거래소 공식 캔들은 **거래가 없어도 행을 만든다.** 거래량 0, 가격은 직전 종가다.
마감 동시호가(15:20~15:30)가 매일 그렇고, 실측에서 확인했다.

```
15:20  000660  volume=0  close=1614000
15:21  000660  volume=0  close=1614000
```

이벤트타임 텀블링 윈도는 **이벤트가 있어야 윈도가 생긴다.** 그래서 이 파이프라인은
그 구간에 아무 행도 만들지 않는다. **"1분 캔들" 이라는 같은 말이 두 정의를 가리킨다.**

채우려면 처리시간 트리거나 사후 채움 단계가 필요하다. 하지 않은 이유는 이렇다.

- **이벤트타임 정확성과 맞바꿔야 한다.** 처리시간으로 윈도를 닫으면 늦게 온
  체결을 어디에 넣을지가 다시 문제가 되고, 이 프로젝트가 검증하려는 것이 바로 그 부분이다.
- **정답지와의 대조에는 영향이 없다.** `verify.sh` 는 INNER JOIN 이므로
  양쪽에 다 있는 윈도만 채점한다. 없는 구간은 모수에서 빠질 뿐 수치를 틀리게 하지 않는다.

**대신 대가가 있다.** 거래가 뜸한 구간에서는 **"출력이 없는 것" 과 "장애" 가
구별되지 않는다.** 둘 다 "행 없음" 으로 나타나기 때문이다.
그래서 신선도 알람(`NoCandlesProduced`)이 캔들만 보지 않고
**체결 유입을 함께 본다.** 그 설계가 마감 동시호가에서 실제로 값을 했다 —
10분간 캔들이 0이었지만 체결도 0이었으므로 알람은 울리지 않았다.
자세한 것은 `failure-notes.md` 의 "마감 동시호가에 워터마크가 10분간 멈춰 섰다".
