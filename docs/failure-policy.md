# 실패 정책과 운영 기준

> 이 파이프라인은 **장기 실행 프로세스**다. "실패하면 어떻게 되는가" 를 미리 정하지 않으면
> 실패했을 때가 아니라 **실패한 줄 모르는 동안**이 문제가 된다.
> 아래 수치는 전부 이 저장소에서 실측한 것이다.

## 1. 분류 원칙 — 멈출 것인가 버릴 것인가

| | 멈춘다 (예외를 올린다) | 버린다 (세고 넘어간다) |
|---|---|---|
| 언제 | **재시도하면 성공할 수 있는** 실패 | 재시도해도 같은 결과인 실패 |
| 예 | 싱크 연결 실패, 네트워크 단절 | 깨진 JSON, 숫자가 아닌 가격 |
| 이유 | 멈춰야 체크포인트가 실패하고 그 지점부터 다시 처리된다 | 멈추면 **재시작 → 같은 레코드 → 재시작 루프**에 빠진다 |

**이 구분을 틀리면 두 방향으로 나쁘다.**
- 버려야 할 것에 멈추면 → 포이즌 필 하나가 파이프라인을 영구 정지시킨다
- 멈춰야 할 것을 버리면 → **데이터가 사라진 채 잡은 건강해 보인다.** 최악이다

## 2. 실패 유형별 현재 정책

| 실패 | 정책 | 계측 | 근거 / 대가 |
|---|---|---|---|
| **소스 WebSocket 단절** | 지수 백오프 재연결(1s→30s) | `reconnects_total{reason}` | 재연결 구간의 체결은 **되메울 수 없다.** 소스에 시퀀스가 없다 |
| **소스 핸드셰이크 401** | 토큰 강제 재발급 후 재시도 | 로그(원인 체인) | 원인이 **동시 연결 수 제한**이면 토큰을 다시 받아도 소용없다. 두 원인을 구분하려고 원인 체인을 로그에 남긴다 |
| **깨진 JSON** | 버린다 | `malformedJsonRecords` | 멈추면 재시작 루프. **버린 원본은 어디에도 남지 않는다 → 3절 공백** |
| **가격/수량 누락** | 버린다 | `missingFieldRecords` | 계측 가능한 위치(역직렬화)에서 거른다. 집계 단계는 `RuntimeContext` 가 없어 메트릭을 못 붙인다 |
| **늦게 도착한 체결** | 사이드 아웃풋으로 보내고 버린다 | `lateTradesDropped` | 이 수치가 없으면 공식 캔들과의 차이를 설명할 수 없다. **원본은 남지 않는다 → 3절 공백** |
| **ClickHouse 적재 실패** | 3회 재시도 후 **예외를 올린다** | `clickhouse*FlushFailures` | 삼키면 데이터가 사라진 채 잡이 건강해 보인다. 예외를 올려야 체크포인트가 실패하고 재처리된다 |
| **TaskManager 사망** | 체크포인트에서 자동 복구 | `numRestarts`, `lastCheckpointDuration` | 실측 **5.4초**(강제 종료 기준). OOM·노드 장애로 조용히 죽으면 하트비트 타임아웃 **50초** |
| **잡 재배포** | savepoint 로 상태 인계 | `FlinkDeployment.upgradeMode` | `cancel` 후 재시작하면 진행 중이던 윈도가 **−67%** 잘린다(실측) |

## 3. 버려진 데이터는 어디로 가는가 — dead letter

처음에는 깨진 레코드와 늦은 체결을 **세기만 하고 버렸다.**
카운터는 "몇 건인지" 만 말해 준다. 이런 질문에는 답하지 못한다.

- 특정 종목에만 몰렸는가, 특정 시각에 몰렸는가
- 소스 형식이 바뀐 것인가, 우리 파서가 틀린 것인가
- 버린 것을 지금이라도 되살릴 수 있는가

**"조용히 사라지는 것은 반드시 계측한다" 는 원칙을 절반만 지킨 상태였다.**
세고는 있지만 되살릴 수는 없었다.

`rtp.dead_letters` 에 **원본 페이로드와 버린 이유**를 남긴다.

| 컬럼 | 내용 |
|---|---|
| `stage` | `deserialize` / `window` — 어느 단계에서 버렸는가 |
| `reason` | `malformed-json` / `missing-field` / `missing-symbol` / `late-window` |
| `payload` | 원본. 앞 2,000자까지. 통째로 넣으면 형식이 바뀐 날 테이블이 폭발한다 |
| `job_run` | 어느 실행이 버렸는가 |

`TTL 14 DAY` 로 잘라낸다. `rtp.dead_letter_summary` 뷰로 단계·이유별 집계를 보고,
`scripts/verify.sh` 에도 넣어 검증할 때마다 눈에 들어오게 했다.

**적재 실패는 삼킨다.** dead letter 를 쓰다 실패해서 본 파이프라인이 멈추면
본말이 전도된다. 대신 실패도 지표로 남긴다 —
**버린 것을 남기는 데 실패한 것조차 조용히 넘어가지 않게.**

**멈추지 않는 것으로는 부족하다. 느리게 만들어서도 안 된다.**
처음 구현은 예외를 삼키기만 했지 한 건마다 동기 HTTP 를 호출했다.
늦은 체결이 한 번에 4,255건 몰린 적이 있는데, 그 조건이면 처리 스레드가
그 수만큼 블로킹 요청에 묶인다. 지금은 유한한 큐에 넣고 별도 스레드가 묶어 적재한다.
큐가 가득 차면 기다리지 않고 버리되 그 건수를 센다 —
dead letter 를 지키려다 TaskManager 를 잃는 것이 더 나쁘다.

| 지표 | 뜻 |
|---|---|
| `deadLetterQueueDropped` | 큐 포화로 기록조차 못 한 건수 |
| `deadLetterWriteFailures` | 적재를 시도했다 실패한 건수 |
| `deadLetterWritten` | 실제로 적재된 건수 |

## 3-b. 큐 앞과 큐 뒤는 장애의 성격이 다르다

같은 날 30분 사이에 두 지점을 끊어 보고 나온 결론이다.

| | 소스(수집기) 단절 | 처리(JobManager) 정지 |
|---|---|---|
| 멈춘 시간 | **2.226초** | **53초** |
| 거래량 손실 | **−1.65 ~ −1.80%** | **0** |
| 복구 | **불가능** | 자동(53초) |

**23배 오래 멈춘 쪽이 아무것도 잃지 않았다.** 차이는 중간에 Kafka 가 있는가뿐이다.

- **큐 뒤쪽**(Flink·ClickHouse)은 멈춰도 **느려질 뿐**이다.
  Kafka 보존 기간 안에 복구하면 밀린 것을 그대로 따라잡는다.
- **큐 앞쪽**(수집기 ↔ 거래소)은 멈추면 **없어진다.**
  토스 스트림에는 체결 ID 도 과거 조회 API 도 없어 되메울 방법이 아예 없다.

이 구분이 우선순위를 정한다.

| | 방침 |
|---|---|
| 소스 단절 | **깨운다.** 고칠 수 있어서가 아니라 잃는 구간이 길어지지 않게 |
| 처리 지연 | 대시보드. Kafka 보존 기간이 실질적인 여유다 |
| 배포 | 재배포는 그 자체로 소스 단절이다 — **배포할 때마다 그 윈도가 1~2% 깎인다** |

> 복구 시간을 잴 때 **무엇을 재는지** 분명히 해야 한다.
> 수집기 파드 교체는 17초 걸렸지만 체결이 실제로 끊긴 것은 2.2초였다.
> 손실의 크기를 정하는 것은 앞의 숫자가 아니라 뒤의 숫자다.

## 4. SLI / SLO

측정 가능한 것만 적는다. 근거는 전부 실측이다.

| SLI | 정의 | 목표 | 실측 |
|---|---|---|---|
| **집계 정확도** | 공식 캔들과 OHLCV 가 정확히 일치한 윈도 비율 | 100% | 566윈도 중 **99.29%** (compose, 08:00~12:52). 쿼리와 원본 출력은 `validation.md` |
| **소스 유실률** | `recv_seq` 공백 / 수신 건수 | < 0.1% | **0%** (체결 303,112건 연속) |
| **데이터 신선도** | 최신 캔들의 지연 | < 3분 | 미측정 |
| **복구 시간** | TaskManager 사망 → 처리 재개 | < 60초 | **5.4초**(강제 종료) / 50초(무응답) |

### 목표를 100% 로 두는 이유

정확도에 여유를 두면 **"허용 오차 안이니 괜찮다" 로 진짜 오차가 숨는다.**
실제로 그럴 뻔했다 — 거래량이 평균 59% 어긋났을 때 소스가 lossy 하다는 것을 알고 있어
"유실이니 어쩔 수 없다" 로 넘어갈 수 있었다. 오차의 **부호 분포**를 본 덕에
정렬 문제라는 것이 드러났고, 고치니 100% 가 됐다.

**근사 비교를 쓰지 않는 것도 같은 이유다.** `Decimal` 정확 비교이므로
1 이라도 다르면 불일치로 잡힌다.

## 5. 알람 — 깨울 것과 대시보드에 둘 것

| 신호 | 등급 | 이유 |
|---|---|---|
| 신선도 위반 (장 시간 중 N분 무갱신) | **깨운다** | 데이터가 안 나오는데 잡은 건강해 보이는 상황이 실제로 있었다(유휴 파티션) |
| 소스 연결 끊김 지속 | **깨운다** | 그 구간은 되메울 수 없다 |
| 체크포인트 연속 실패 | **깨운다** | 싱크가 막혔다는 뜻이고, 방치하면 재처리 구간이 계속 늘어난다 |
| 늦은 체결 드롭 급증 | 대시보드 | 정확도에 영향은 있으나 즉시 조치할 것이 없다 |
| 중복 기록(`write_count>1`) | 대시보드 | at-least-once 의 정상 동작이다. 추세만 본다 |
| 컨슈머 lag | 대시보드 | **그룹별로 봐야 한다.** 죽은 그룹이 lag 을 무한히 쌓아 전체 합계는 무의미하다(실측). 쌓인 것만으로는 신호가 아니고 **높으면서 늘어나는 중**일 때만 본다 |
| 읽히지 않는 파티션 | **깨운다** | lag 으로는 절대 안 잡힌다 — 아래 참고 |

### lag 은 건강 신호로 충분하지 않다

lag 은 **"내가 아는 일을 얼마나 밀렸는가"** 이지
**"내가 해야 할 일을 다 알고 있는가"** 가 아니다. 이 차이로 한 번 당했다.

토픽 파티션을 3에서 7로 늘렸더니 두 종목이 새 파티션으로 옮겨 갔는데,
Flink 는 파티션 재발견이 기본 꺼짐이라 새 파티션을 영원히 읽지 않았다.

| 무엇 | 값 |
|---|---|
| 잡 상태 | `RUNNING / STABLE` |
| 컨슈머 lag | **0** |
| kafka-exporter 그룹 lag 합계 | **−5** (커밋 없는 파티션은 −1) |
| 실제로 쌓인 미처리 레코드 | **10,531건** |
| 캔들 출력 | **0** |

lag 이 장애를 감추는 데 그치지 않고 **부호가 뒤집히면서 적극적으로 거짓말을 한다.**
그래서 두 가지를 둔다.

1. **신선도**(`NoCandlesProduced`) — 유입은 있는데 출력이 없으면 깨운다.
   lag 이 무엇을 말하든 이 신호는 정직하다.
2. **읽히지 않는 파티션**(`PartitionNotConsumed`) — 데이터가 있는데
   커밋 오프셋이 없는 파티션을 직접 본다. 양성·음성 모두 실측으로 확인했다.

자세한 것은 `failure-notes.md` 의
"파티션을 늘렸더니 파이프라인이 멈췄는데 lag 은 0이었다".

### 규칙을 쓰는 것과 알람이 동작하는 것은 다르다

위 표를 `charts/rtp/files/prometheus/alerts.yml` 로 옮겨 적어 두고
**동작한다고 믿고 있었다.** 실제로는 `prometheus.yml` 에 `rule_files` 가 없어
규칙이 한 번도 평가되지 않았다. 파드는 Running 이었고 `helm lint` 도 통과했다.
자세한 것은 `failure-notes.md` 의 "알람을 8개 썼는데 Prometheus 가 한 번도 평가하지 않았다".

그래서 **계측 자신을 계측하는 규칙**을 넣었다.

| 규칙 | 무엇을 잡나 |
|---|---|
| `AlertRulesNotLoaded` | 규칙 파일이 로드되지 않았거나 문법이 깨졌다 |
| `AlertmanagerUnreachable` | 발화해도 전달될 곳이 없다 |
| `ScrapeTargetDown` | 빈 그래프를 정상으로 읽는 것을 막는다 |

### 실제 통보 채널은 붙이지 않았다

Alertmanager 까지는 클러스터에 있고 라우팅·묶음·억제가 실제로 동작한다
(소스가 끊겼을 때 `IngesterDisconnected` 가 `NoCandlesProduced` 를 억제하는 식).
다만 **최종 수신처는 없다.** 공개 저장소라 웹훅 URL 을 커밋할 수 없다.

따라서 이 프로젝트에서 `severity: page` 는 "실제로 사람을 깨운다" 가 아니라
**"깨워야 할 등급으로 분류하고 그 경로까지 배선해 두었다"** 는 뜻이다.
그 차이를 흐리지 않기 위해 적어 둔다.

### 장 운영 시간을 모르면 신선도 알람은 성립하지 않는다

20:00 이후 유입 0은 **정상**이고 09:00에 0이면 **장애**다.
같은 지표가 시간대에 따라 반대 의미가 된다.
실제로 이 구분이 없어 멀쩡한 수집기를 장애로 오진한 적이 있다.

## 6. 초록불인데 고장난 경우들 (실측)

이 파이프라인에서 실제로 겪은 것만 적는다. **전부 지표는 정상이었다.**

| 상황 | 겉보기 | 실제 |
|---|---|---|
| 유휴 파티션 | RUNNING, 체크포인트 성공, 백프레셔 0, lag 정상 감소 | 윈도가 **하나도 닫히지 않음** |
| 유령 컨슈머 그룹 | lag 89,188 (빨간불) | 시스템은 멀쩡. 취소된 잡의 그룹이 쌓고 있었음 |
| K8s 첫 배포 | RUNNING\|STABLE, 체크포인트 10초마다 성공 | 토픽이 비어 있어 **빈 상태를 저장** 중이었음 |
| 수집기 카운터 정지 | 카운터 두 번 읽어 동일 → 장애로 판단 | 60초 주기 지표를 25초 간격으로 읽은 것. 정상이었음 |
| 파티션 재배정 | RUNNING\|STABLE, **lag 0** (exporter 합계는 −5) | 새 파티션에 1만 531건이 읽히지 않고 쌓임. 출력 0 |
| 알람 8개 | 파드 Running, `helm lint` 통과, 파일도 존재 | `rule_files` 누락으로 **한 번도 평가되지 않음** |
| 실험 잡 계측 | 스크레이프 타깃 `up` | Flink 지표를 **하나도 안 내보냄**(리포터 미설정) |
| GitOps 동기화 | `Synced / Healthy`, 리비전도 HEAD | diff 계산이 실패해 **이전 리비전이 적용된 채** |

**공통점: 성공 기준을 프로세스 상태로 잡았기 때문이다.**
파이프라인의 성공 기준은 `Pod: Running` 이 아니라 **처리한 건수와 결과의 정확성**이어야 한다.
`scripts/verify.sh` 가 그 기준을 고정해 둔 것이고,
`matched == 0` 이면 정확도를 주장하지 못하게 판정 문구를 넣어 두었다.

### 계측 자신도 같은 함정에 빠진다

위 표의 뒤쪽 세 줄은 파이프라인이 아니라 **파이프라인을 감시하는 장치**가 고장난 것이다.
감시 장치가 조용히 죽어 있으면 그 아래 모든 초록불의 의미가 사라진다.

그래서 계측을 계측하는 규칙을 따로 둔다.

| 규칙 | 무엇을 잡나 |
|---|---|
| `AlertRulesNotLoaded` | 규칙 파일이 로드되지 않았거나 문법이 깨졌다 |
| `AlertmanagerUnreachable` | 발화해도 전달될 곳이 없다 |
| `ScrapeTargetDown` | 빈 그래프를 정상으로 읽는 것을 막는다 |
| `PartitionNotConsumed` | lag 이 감추는 미처리 파티션을 직접 본다 |

그리고 `scripts/verify.sh` 0번이 **ArgoCD 가 실제로 적용한 리비전**을 HEAD 와 대조한다.

> **계측은 "붙였다" 로 끝나지 않는다. "값이 보인다" 까지가 한 벌이고,
> 그 값이 남아 있어야 사후에 쓸 수 있다.**
> Prometheus 를 `emptyDir` 로 두었다가 장애 실험 세 건의 파형을 잃고 PVC 로 옮겼다.
