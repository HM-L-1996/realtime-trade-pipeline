- [ ] **순서 보장 깨짐** — 파티션을 늘렸을 때 종목별 순서가 어떻게 되는가
- [ ] **소스 연결 끊김** — 재연결 중 유실 구간을 어떻게 메우는가
- [ ] **유휴 파티션과 워터마크 정지** — 종목 2개 / 파티션 3개라 파티션 하나는 항상 비어 있다.
      Flink 워터마크는 모든 파티션의 최소값을 따라가므로, 유휴 파티션이 있으면
      워터마크가 전진하지 않고 **윈도우가 영원히 닫히지 않는다.**
      `withIdleness()` 유무로 결과가 어떻게 갈리는지 확인할 것.
      (2026-08-30 합성 데이터 주입 중 발견 — 실제로 재현되는지는 Flink 잡 작성 후 확인)

## 실제로 겪은 것

### PING 을 한 번도 못 보내고 90초마다 재연결하던 수집기

**일으킨 방법:** 의도한 것이 아니다. 문서만 보고 짠 수집기를 처음으로 실서버에 붙였다.

**증상:** 장외라 체결이 안 흐르는 상태에서 프로브를 돌렸는데,
`[4/4] 텍스트 PING 전송` 로그가 아예 찍히지 않고 `closeReason=recv-timeout` 으로 끝났다.

**원인:** `poll()` 이 수신 타임아웃(90초)만큼 블로킹하는 구조였다. PING 주기는 60초.
프레임이 오지 않으면 poll 이 90초를 통째로 잡아먹고, 그 사이에 60초 PING 시점이 지나간다.
루프가 다시 돌 때는 이미 유휴 타임아웃이라 연결을 끊는다.
**즉 프레임이 뜸한 구간에서는 keepalive 가 구조적으로 불가능했다.**
장이 열려 거래가 활발하면 프레임이 계속 와서 드러나지 않는다 —
장 초반, 거래 뜸한 종목, 점심시간에만 재연결이 반복되는 형태로 나타났을 것이다.

**대응:** poll 을 1초씩 끊어 기다리고, 유휴 판정은 "마지막 수신 시각" 으로 직접 하도록 분리했다.
대기 시간을 호출자가 정하게 바꾼 것이 핵심이다.

**검증:** 수정 후 수집기를 띄워두니 60초 시점에
`rtp_ingester_frames_total{frame_type="pong"}` 이 1 로 증가했고, 재연결 0회로 유지됐다.

**남은 문제:** 이 버그는 계측이 있어서 잡혔다. `frames_total` 을 frame_type 별로
쪼개두지 않았다면 "재연결이 잦다" 까지만 알고 원인을 못 찾았을 것이다.
장애 실험 전에 계측을 먼저 붙인 판단이 여기서 값을 했다.

### 정답지를 1분 어긋나게 읽고 있었다

**일으킨 방법:** 의도한 것이 아니다. 공식 캔들 대조를 처음 돌렸다.

**증상:** 거래량이 평균 59% 어긋났다. 최대 417%. 종가는 84건 중 39건만 맞았다.

**함정:** 소스 스트림이 lossy 하다는 것을 이미 알고 있었다. 그래서 "프레임 유실 때문" 이
가장 그럴듯한 설명이었고, 실제로 그렇게 결론 내릴 뻔했다.

**원인:** 막은 것은 **오차의 부호**였다. 내 쪽이 적은 게 44건, 많은 게 40건 —
양방향이었다. 유실이라면 한쪽으로만 어긋나야 한다. 값이 새는 게 아니라 정렬이 어긋난 모양이다.
1분씩 밀어 대조해 보니 +60초에서 **84/84 완전 일치**했다.
공식 캔들의 `timestamp` 가 윈도 시작이 아니라 **종료** 시각이었다. API 문서에 없는 사실이다.

**대응:** 적재 시점에 시작 시각으로 정규화했다. 컬럼 이름이 `window_start` 이므로
종료 시각을 그대로 넣으면 이 테이블을 쓰는 모든 쿼리가 조용히 1분씩 어긋난다.

**남은 문제:** 이 버그는 "집계가 틀렸다" 로 오진하기 매우 쉬웠다.
워터마크를 만지거나 유실률을 조사하는 쪽으로 며칠을 쓸 수도 있었다.
**오차의 크기가 아니라 분포를 먼저 본 것이 갈림길이었다.**

### 컨슈머 lag 이 89,188 인데 시스템은 멀쩡했다

**일으킨 방법:** 의도한 것이 아니다. 장중에 파이프라인 상태를 확인하다 발견했다.

**증상:** `sum(kafka_consumergroup_lag{topic="trades.raw"})` 가 89,188.
초당 60건 유입이니 25분치가 밀린 셈이다. 그런데 같은 시각에
백프레셔 0, 체크포인트 79ms, 캔들은 공식과 100% 일치하고 있었다.
**지표와 실제가 정면으로 어긋났다.**

**원인:** 그룹별로 쪼개 보니 갈렸다.

```
rtp-candle-1m     lag=89,817   <- 취소된 잡의 그룹
rtp-candle-live   lag=451      <- 실제로 도는 잡
```

죽은 컨슈머 그룹은 오프셋이 그 자리에 멈춘 채 남는다. 토픽에 데이터가 들어올수록
**lag 이 무한히 자란다.** 잡을 재배포하며 group-id 를 바꿨더니 유령이 하나 생긴 것이다.

**대응:** `kafka-consumer-groups.sh --delete --group rtp-candle-1m`.
정리 후 lag 247 로 떨어졌다.

**남은 문제:** 이건 K8s 로 옮기면 더 자주 만난다. 잡을 재배포할 때마다 group-id 를
바꾸는 습관이면 유령이 계속 쌓이고, lag 알람은 매번 오탐이 된다.

두 가지 중 하나를 골라야 한다.
- group-id 를 고정하고 savepoint 로 상태를 넘긴다 (유령이 안 생긴다)
- group-id 를 바꾸되 배포 절차에 이전 그룹 삭제를 포함한다

**전자가 맞다.** 후자는 사람이 빠뜨리면 그대로 쌓인다.
그리고 group-id 를 고정해야 savepoint 재배포 실험 자체가 성립한다.

> 대시보드 교훈: lag 을 **그룹별로 쪼개 보지 않으면** 이 상황이 "Flink 가 못 따라간다" 로만
> 보인다. 전체 합계 하나만 걸어둔 알람은 유령 때문에 영원히 울린다.

### TaskManager 를 재시작했더니 잡이 복구되지 못하고 FAILED 로 끝났다

**일으킨 방법:** 설정 비교 실험을 하려는데 슬롯이 부족했다(`NoResourceAvailableException`).
TaskManager 슬롯을 3개에서 6개로 늘리려고 컨테이너를 재생성했다.
체크포인트에서 복구될 것으로 기대했다.

**증상:** 3분을 기다려도 잡이 RUNNING 으로 돌아오지 않았다. 상태는 `FAILED`.
정작 TaskManager 는 정상 등록되어 슬롯 6개가 비어 있었다.

**원인:**

```
org.apache.flink.runtime.JobException: Recovery is suppressed by
FixedDelayRestartBackoffTimeStrategy(maxNumberRestartAttempts=10, backoffTimeMS=5000)
```

잡 코드에 `RestartStrategies.fixedDelayRestart(10, 5_000L)` 을 박아 뒀다.
**10회 x 5초 = 50초.** 컨테이너가 이미지 기동 → 등록까지 그보다 오래 걸렸고,
잡은 그 전에 시도를 다 쓰고 포기했다. 재시작 이력을 보면
11:40:13, 11:40:18, 11:40:24 로 5초 간격으로 소진하고 끝났다.

**대응:** 두 가지를 고쳤다.

1. **지수 백오프로 변경** — 초기 5초, 최대 2분, 배수 2.0.
   10분간 장애가 없으면 백오프를 초기화한다(없으면 한 번 길어진 백오프가 영원히 유지된다).
2. **재시작 전략을 잡 코드에서 클러스터 설정으로 옮겼다.**
   이건 잡 로직이 아니라 운영 정책이고, 환경마다 달라야 한다.
   로컬 컨테이너와 K8s Pod 의 복귀 시간은 다르다.

**남은 문제:** 이 설정으로 실제 복구되는지는 아직 확인하지 않았다. 다시 죽여봐야 한다.

> **K8s 이전 전에 이걸 만난 것이 다행이다.** Pod 재스케줄은 컨테이너 재생성보다 느리다.
> `failure-notes` 의 "TaskManager Pod 강제 종료" 실험을 K8s 에서 처음 했다면
> 클러스터 문제로 오진했을 것이다 — 실제로는 잡 설정 문제였다.
> CLAUDE.md 의 "docker-compose 로 먼저 동작시킨 뒤 K8s 로 옮긴다" 가 값을 한 사례다.

### 워터마크 지연을 0으로 줘도 늦은 데이터가 안 버려졌다

**일으킨 방법:** `validation.md` 의 "설정 변경에 따른 정확도 변화" 표를 채우려고
리플레이로 지연 도착을 주입하고 워터마크 지연 0 / 60 / 300초를 비교했다.

**증상:** 세 조건이 **완전히 같은 결과**를 냈다. 14윈도, 8,000건, 거래량 315,220,
늦어서 버린 체결 0. 설정을 바꿨는데 아무 차이가 없었다.

**첫 갈림길 — 메커니즘 고장인가 아닌가:**
`lateTradesDropped` 메트릭이 **값 0으로 존재한다**는 점이 첫 단서였다.
카운터를 `open()` 에서 등록하므로, `open()` 이 안 불렸다면 메트릭 자체가 없어야 한다.
즉 카운터는 붙었고 사이드 아웃풋에 진짜로 아무것도 안 온 것이다.

그래도 확실히 하려고 손으로 체결 3건을 만들어 넣었다 —
`T`(윈도 A) → `T+300초`(A를 닫는다) → `T+30초`(이제 늦음).
세 번째가 정확히 버려지고 카운터가 1이 됐다. **메커니즘은 정상이다.**

**원인:** 조건을 하나씩 바꿔가며 재봤다. 전부 워터마크 지연 0초, 같은 입력이다.

| 파티션 | 소비 상태 | 드롭 |
|---|---|---|
| 1 | 실시간 추종 | 4,255 |
| 3 | 실시간 추종 | 460 |
| 3 | 캐치업 | 0 |

워터마크는 200ms 주기로 "본 최대 이벤트타임 − 지연" 으로 만들어진다.
어떤 레코드가 처리되는 순간 워터마크가 얼마나 가 있는지는 **설정이 아니라 그때의 소비 상황**이 정한다.

- 워터마크는 파티션별 값의 **최소**다. 파티션마다 소비 속도가 어긋나면
  최소값이 뒤처지고 그만큼 늦은 데이터가 살아남는다
- 캐치업 중에는 200ms 한 틱에 수천 건이 지나가 워터마크가 처리 위치를 못 따라간다

**대응:** 코드를 고칠 것이 없다. 고칠 것은 **해석**이다.
워터마크 지연은 "최소한 이만큼 기다린다" 는 하한이지 실제 허용치가 아니다.

**남은 문제 — 이게 더 중요하다:**
**같은 잡이 밀렸다가 따라잡는 동안과 실시간을 유지할 때 서로 다른 결과를 낸다.**
라이브 파이프라인이 공식 캔들과 99% 일치한 것도 파티션 3개 + 실시간 유지라는
조건의 여유 덕일 수 있다. **그 정확도는 설정이 보장한 것이 아니다.**
부하가 올라가 잡이 밀리기 시작하면 같은 설정으로도 결과가 달라질 수 있다.
이것을 확인하려면 백프레셔를 걸어 잡을 일부러 밀리게 한 뒤 정확도를 재야 한다.

> 유한한 리플레이는 마지막 윈도들이 닫히지 않아 그대로는 비교가 안 된다.
> 종목마다 **미래 시각 센티널 레코드**를 하나씩 넣어 워터마크를 밀어야 전부 닫힌다.

### 잡을 재시작했더니 같은 윈도가 두 번 쓰였다 (at-least-once 실증)

**일으킨 방법:** 의도한 것이 아니다. TaskManager 를 재생성한 뒤 라이브 잡을 다시 제출했다.

**증상:** `write_count > 1` 인 윈도가 **420개**. 직전 측정에서는 0이었다.
거래량 정확도는 99.29% 로 유지됐다 — `candles_1m_dedup` 이 `argMax(ingested_at)` 로
마지막 기록을 고르기 때문이다.

**원인:** 잡이 `OffsetsInitializer.earliest()` 로 읽는다. 재제출하면
**토픽 전체를 다시 처리**하고, 이미 적재된 윈도를 한 번 더 쓴다.
싱크는 at-least-once 이고 멱등하지 않으므로 그대로 두 번째 행이 쌓인다.

리플레이·재처리 실험을 위해 일부러 earliest 로 둔 설정이라 코드 버그는 아니다.
하지만 **운영에서 이 설정으로 재배포하면 매번 전체 중복이 생긴다.**

**대응:** 아직 고치지 않았다. 선택지가 갈린다.
- `OffsetsInitializer.committedOffsets(EARLIEST)` — 그룹의 커밋 오프셋에서 이어 읽는다.
  재배포 시 중복이 없다. 대신 재처리 실험을 하려면 별도 group-id 가 필요하다
- savepoint 로 재배포 — 상태와 오프셋을 함께 넘긴다. 정석이지만 절차가 늘어난다

**남은 문제 — 이 항목이 존재한다는 사실 자체가 결과다:**
캔들 테이블을 `ReplacingMergeTree` 로 뒀다면 중복이 백그라운드 머지에서 조용히 접혀
**이 사건을 관측조차 못 했을 것이다.** `MergeTree` + `write_count` 로 둔 판단이
여기서 값을 했다. exactly-once 가 지켜지는지를 "설정이 켜져 있다" 가 아니라
결과로 확인한다는 것이 이런 의미다.
