# 장애 실험 노트

> **이 문서가 이 저장소의 핵심 산출물이다.**
> 각 항목은 "무엇을 일으켰나 → 어떻게 드러났나 → 왜 그랬나 → 어떻게 고쳤나" 순서로 쓴다.

## 실험 목록

- [ ] **지연 도착 데이터** — 워터마크 설정에 따라 집계가 어떻게 틀어지는가. allowed lateness 트레이드오프
- [ ] **컨슈머 lag 누적** — 처리량이 유입을 못 따라갈 때 백프레셔가 어디서 발생하고 어떻게 관측되는가
- [ ] **장애 후 재처리** — 체크포인트 복구 시 중복/누락이 생기는가. exactly-once가 실제로 지켜지는지 **결과로 검증**
- [ ] **순서 보장 깨짐** — 파티션을 늘렸을 때 종목별 순서가 어떻게 되는가
- [ ] **소스 연결 끊김** — 재연결 중 유실 구간을 어떻게 메우는가
- [ ] **유휴 파티션과 워터마크 정지** — 종목 2개 / 파티션 3개라 파티션 하나는 항상 비어 있다.
      Flink 워터마크는 모든 파티션의 최소값을 따라가므로, 유휴 파티션이 있으면
      워터마크가 전진하지 않고 **윈도우가 영원히 닫히지 않는다.**
      `withIdleness()` 유무로 결과가 어떻게 갈리는지 확인할 것.
      (2026-08-30 합성 데이터 주입 중 발견 — 실제로 재현되는지는 Flink 잡 작성 후 확인)

### K8s 배포 이후 (스트리밍 워크로드 고유)

- [ ] **TaskManager Pod 강제 종료** — 체크포인트에서 복구되는가, 상태는 온전한가, 복구에 얼마나 걸리는가
- [ ] **savepoint 기반 무중단 재배포** — 잡 코드를 바꿔 배포할 때 상태를 넘길 수 있는가
- [ ] **백프레셔 상황의 오토스케일** — 스케일아웃이 실제로 도움이 되는가, 상태 재분배 비용이 더 크지는 않은가
- [ ] **JobManager 장애** — HA 구성 유무에 따라 어떻게 달라지는가

### 관측성

- [ ] **각 실험이 대시보드에서 어떻게 보였는가** — 장애가 났을 때 무엇을 보고 알아챌 수 있는지가 핵심.
      컨슈머 lag, 체크포인트 소요시간, 백프레셔 지표
- [ ] **데이터 신선도 SLO** — "최근 캔들이 N분 이상 갱신되지 않으면 알림". 잡이 살아있는 것과
      데이터가 제때 반영되는 것은 다르다
- [ ] **알람 설계** — 무엇을 깨우는 알람으로 두고 무엇을 대시보드로 둘 것인가
