# 검증 결과

내 집계 캔들 vs 거래소 공식 캔들 대조.

## 방법

- **대상**: `005930`(삼성전자), `000660`(SK하이닉스)
- **비교 항목**: O/H/L/C/V 전부. 가격은 `Decimal64(4)`, 거래량은 `Decimal64(8)` 로 **정확 비교**한다.
  부동소수 근사 비교를 쓰지 않는 이유는 그 순간 "허용 오차" 를 정해야 하고,
  그러면 진짜 오차가 허용 오차 뒤에 숨기 때문이다.
- **쿼리**: `rtp.candle_diff` 뷰 (`infra/clickhouse/init/02_views.sql`)
- **중복 판정**: `candles_1m_dedup.write_count`. 1이 아니면 같은 윈도가 두 번 쓰인 것

```sql
SELECT count() AS n_official,
       countIf(missing = 1)                      AS n_missing,
       countIf(missing = 0)                      AS n_matched,
       countIf(missing = 0 AND close_diff = 0)   AS n_close_exact,
       countIf(missing = 0 AND volume_diff = 0)  AS n_vol_exact,
       countIf(missing = 0 AND write_count > 1)  AS n_dup
FROM rtp.candle_diff;
```

`000660` 도 −641 / +641 로 같은 모양이다. **유실이 아니라 경계 배정 차이다.**

#### 파이프라인 결백은 증명됐다

보관해 둔 원본 체결(`trades_raw`)에서 직접 집계한 값이 내 캔들과 **정확히 같다**.

```
09:05  raw_volume 148,625  = 내 캔들 148,625
09:06  raw_volume 387,392  = 내 캔들 387,392
```

즉 **Flink 집계는 자기 입력과 완벽히 일치한다.** 유실도 오배치도 없었다.
차이는 "내가 받은 체결의 타임스탬프" 와 "거래소가 봉을 나눈 기준" 사이에 있다.
`recv_seq` 연속성도 공백 0이므로 수집 구간 유실도 아니다.

#### 아직 설명하지 못한 것

경계 직후(`09:06:00.024`~`.062`) 체결 4건의 합이 **2,443** 인데 필요한 값은 **2,388** 이다.
55 만큼 어긋나므로 "시간 순 앞부분을 잘라 옮기면 맞는다" 는 설명이 성립하지 않는다.
경계 포함 규칙 차이(`(T-60s, T]` vs `[T, T+60)`) 가설도 기각됐다 —
127,631건 중 정각에 걸린 체결은 1건뿐이다.

확실한 단서는 하나다. 그 체결들의 **수신 시각이 이벤트 시각보다 이르다.**

```
event 09:06:00.024  <- 수신 09:05:59.943  (80ms 앞섬)
```

소스 시계가 우리보다 앞서 있다. 거래소 내부의 봉 분할 기준이 발행하는 틱 타임스탬프와
다를 가능성이 있으나 **아직 증거가 없다.** 다음 확인 대상으로 남긴다.

> 재제출하지 않은 구간에서는 이 현상이 없었다. 잡 재시작과의 인과도 아직 배제하지 못했다.

## 여기까지 오는 데 걸린 함정

### 공식 캔들의 `timestamp` 는 윈도 **종료** 시각이다

첫 대조에서 거래량이 평균 59% 어긋났다. 그런데 차이가 **양방향**이었다 —
내 쪽이 적은 게 44건, 많은 게 40건.

프레임 유실이라면 한쪽으로만 어긋나야 한다. 소스가 lossy 하다는 것을 알고 있었으므로
"유실 때문" 이라고 결론 내리기 쉬운 상황이었는데, **부호가 갈린다는 사실 하나가 그 해석을 막았다.**
양방향 오차는 값이 새는 게 아니라 **정렬이 어긋난** 모양이다.

1분씩 밀어서 대조해 보니 결과가 명확했다.

| 시프트 | 거래량 일치 | 종가 일치 |
|---|---|---|
| 0 | 0 / 84 | 39 / 84 |
| **+60초** | **84 / 84** | **84 / 84** |
| −60초 | 0 / 84 | 23 / 84 |

즉 공식 캔들이 `08:42` 로 표시한 봉은 `08:41:00 ~ 08:42:00` 구간이다.
**API 문서에 이 사실이 없다.** 적재 시점에 시작 시각으로 정규화하도록 고쳤다 —
컬럼 이름이 `window_start` 인데 종료 시각이 들어가 있으면
이 테이블을 쓰는 모든 쿼리가 조용히 1분씩 어긋난다.

> 이 항목이 이 프로젝트에서 가장 값진 결과다. 집계 로직은 처음부터 맞았고,
> 틀린 것은 **정답지를 읽는 방법**이었다. 그리고 그것을 구분해 준 것은
> 오차의 크기가 아니라 **오차의 부호 분포**였다.

## 아직 측정하지 않은 것

  워터마크를 0에 가깝게 줄이거나, 리플레이로 지연 도착을 주입해야 한다.

|---|---|---|---|
| 0초 | 1 | 실시간 추종 | 4,255 |
| 0초 | 3 | 실시간 추종 | 460 |
| 0초 | 3 | 캐치업 | 0 |

동일 입력(리플레이 8,000건, 지연 10% 주입, 최대 180초, seed 7) 기준.

**워터마크 지연 열만 보면 아무 설명력이 없다.** 설명력을 갖는 것은 파티션 수와
소비 상태다. 아래에 원인을 적었다.

### 워터마크 지연만으로는 차이가 나지 않았다 — 원인 규명

리플레이로 지연 도착을 주입해 워터마크 0 / 60 / 300초를 비교했더니
**세 조건이 완전히 같은 결과를 냈다.** 14윈도, 8,000건, 거래량 315,220, 드롭 0.
설정을 바꿨는데 아무 차이가 없다는 것 자체가 신호였다.

먼저 메커니즘이 고장난 것인지부터 갈랐다. 손으로 체결 3건을 만들어
- `T` (윈도 A)
- `T+300초` (워터마크를 A 너머로 밀어 A를 닫는다)
- `T+30초` (윈도 A, 이제 늦음)

투입했더니 세 번째가 정확히 버려지고 `lateTradesDropped = 1` 이 찍혔다.
**메커니즘은 정상이다.** 그러면 리플레이 레코드들이 실제로는 늦지 않았다는 뜻이다.

입력에 늦은 것이 없어서는 아니었다. 종목별(=파티션별)로 세어 보면 분명히 있다.

```
005930  순서 역전 2,195건, 60초 초과 1,436건, 최대 180초
000660  순서 역전 1,956건, 60초 초과 1,265건, 최대 180초
```

조건을 하나씩 바꿔가며 재보니 답이 나왔다. **같은 입력, 같은 워터마크 설정(0초)** 이다.

| 조건 | 파티션 | 소비 상태 | 늦어서 버린 체결 |
|---|---|---|---|
| 수동 3건 | 1 | 실시간 | 1 / 1 |
| 리플레이 8,000건 | 1 | 실시간 추종 | **4,255** |
| 리플레이 8,000건 | 3 | 실시간 추종 | **460** |
| 리플레이 8,000건 | 3 | 캐치업 | **0** |

#### 결론: 워터마크 지연은 실제 허용치를 결정하지 않는다

워터마크는 200ms 주기로 "지금까지 본 최대 이벤트타임 − 지연" 으로 생성된다.
어떤 레코드가 처리되는 순간 워터마크가 얼마나 전진해 있는지는 설정이 아니라
**그 시점의 소비 상황**이 정한다.

- **파티션이 많을수록 여유가 커진다.** 워터마크는 파티션별 워터마크의 **최소값**이다.
  파티션마다 소비 속도가 어긋나면 그 최소값이 뒤처지고, 그만큼 늦은 데이터가 살아남는다.
  파티션 1개 → 3개로 늘리자 드롭이 4,255 → 460 으로 줄었다
- **캐치업 중에는 거의 버려지지 않는다.** 밀린 데이터를 몰아 읽을 때는
  워터마크가 처리 위치를 따라가지 못한다. 200ms 한 틱 사이에 수천 건이 지나간다

**같은 잡이 밀렸다가 따라잡는 동안과 실시간을 유지할 때 서로 다른 결과를 낸다.**
이것이 이 실험에서 나온 가장 중요한 사실이다. 워터마크 지연은
"최소한 이만큼은 기다린다" 는 하한이지, 실제 허용치가 아니다.

> `validation.md` 첫 실측에서 라이브 파이프라인이 공식 캔들과 99% 일치한 것도
> 이 여유 덕을 봤을 수 있다. 파티션 3개에 소비가 실시간을 유지하는 조건이었다.
> **그 정확도는 설정이 보장한 것이 아니다.** 부하가 올라가 잡이 밀리기 시작하면
> 같은 설정으로도 결과가 달라질 수 있다.

#### 이 실험을 재현하려면

유한한 리플레이는 마지막 윈도들이 닫히지 않아 그대로는 비교가 안 된다.
리플레이가 끝난 뒤 **미래 시각의 센티널 레코드**를 종목마다 하나씩 넣어
워터마크를 밀어야 모든 윈도가 닫힌다. 위 결과도 그렇게 얻었다.

- **장 마감 구간** — 마감 동시호가(15:20~15:30)는 아직 대조하지 않았다.
  개장 직후(09:00)는 확인했다 — 체결 1,601건 / 거래량 732,619 로 하루 중 가장 몰리는
  분인데 정확히 일치했다
- **장기 구동** — 아직 두어 시간 구간이다. 체크포인트가 누적되고 상태가 커진 뒤에도
  같은 정확도가 유지되는지는 별개 문제다
- **09:05·09:06 경계 배정 차이의 원인** — 위 참고

## 소스 유실률 (2026-08-31 실측)

`recv_seq` 는 연결별로 1씩 증가하므로 공백이 곧 유실이다.

| 연결 | 수신 | seq 범위 | 공백 | 유실률 |
|---|---|---|---|---|
| `f4ebd52f49ac` (실제 수집기) | 117,730 | 1 ~ 117,730 | **0** | **0%** |

문서가 lossy 하다고 명시한 스트림인데 **이 구간에서는 한 건도 잃지 않았다.**
장 초반 두어 시간, 초당 60건 수준에서의 결과다. 부하가 더 높은 구간이나
장시간 구동에서도 그런지는 별개 문제다.

Kafka → Flink 구간도 확인했다 — 142개 윈도에서 원본 체결 수와 캔들의
`trade_count` 가 전부 일치했다(`rtp.trade_count_check`).

> 이 표가 있어야 "공식 캔들과 다르다" 를 해석할 수 있다.
> 유실률이 0인데 값이 다르면 그건 유실이 아니라 **배정 문제**다 —
> 실제로 09:05·09:06 건이 그렇게 판별됐다.
